# Rung

Rung is a small, dynamically typed programming language with several execution engines, built
to find out how much each classic interpreter technique speeds it up, measured one technique at
a time on the same six benchmark programs:

1. a tree-walking interpreter (the honest, slow baseline),
2. a stack-based bytecode VM,
3. an optimization ladder: computed-goto dispatch, NaN-boxing, a register-based VM,
   superinstructions, inline caching, constant folding, each one switchable and measured alone,
4. a baseline JIT that emits ARM64 machine code for hot integer functions,
5. background JIT compilation on a second thread.

The name comes from the results table: each row is one rung of the ladder, the row before it
plus exactly one change.

Not every rung paid off, and the [results](#results) show that as measured: NaN-boxing made
the stack VM slower on every benchmark, `strcat` (string allocation and garbage collection)
barely moves after the first VM, and the JIT compiles a function in `loop_sum` only, so the top
of its range is that one benchmark and its row matches the one below it on the other five
(marked ‡). Every measurement in this README comes from a committed file in `results/` or from
a counter file in `docs/` that a test regenerates: `scripts/ladder.py` writes the summary above
and the tables below (CI fails if they differ from the results files), and the few figures
quoted in prose name the file they come from. What each rung was expected to do, what it did,
and why they differ is in [`docs/notes.md`](docs/notes.md) §5.

**Status.** All five engines run every Rung program and pass the same conformance suite; the
JIT exists on arm64 only. All nine ladder rows and the background-compilation pair are
measured. Two stretch goals that would let the JIT compile more of the suite are not built:
direct self-recursion (so `fib` could compile, notes D7) and array reads and writes in machine
code (so `sieve` could).

## Results

Every number about speed in this repository comes from one pipeline: `scripts/bench.py` measures
the configurations listed in `scripts/ladder_configs.json` and writes `results/<id>.json`;
`scripts/ladder.py` turns those files into the tables below. CI runs
`python3 scripts/ladder.py --check`, which fails if the tables differ from what the committed
results files generate. The ladder is cumulative (notes D4): row 05 keeps computed goto and
NaN-boxing, row 09 is the register VM with superinstructions, inline caching, folding and the
JIT.

How to read the tables:

- **Regressions stay in.** A cell below 1.00× in the marginal table is marked ▼ and printed in
  bold. Row `04_nanbox` lost on all six benchmarks, and it stays in the ladder because rows 05
  to 09 build on it (the JIT's type guards test NaN-box tags, notes D3, D15).
- **‡ means "the JIT compiled nothing here".** In five of the six benchmarks every hot function
  uses something outside the JIT's whitelist, so those cells measure the register VM plus the
  JIT's hotness counting, not machine code (the footnote under the tables says what each one
  uses).
- **† means "re-measure this".** `loop_sum` under `07_ic` was flagged noisy in every attempt;
  its per-process times fall into groups that are not explained (notes §5, rung 3e).
- **Not every pair of rows was measured together.** The rows come from four `bench.py`
  invocations, so three marginal ratios (`02_stack` over `01_tree`, `07_ic` over `06_super`,
  `09_jit` over `08_fold`) compare runs taken at different times, and differences of a percent
  or two between them are not resolved (notes §5, "How the recorded rows were taken").
- **Background compilation** is the last timing table: `jit_sync` and `jit_background` are not
  ladder rows but the same configuration with and without `--jit-background`, measured
  interleaved. On `bench/warmup.rg`, a plainly labelled warm-up benchmark built so that 64
  functions compile in one short call, the background thread takes the compile pause off the
  engine's thread and the slowest calls get shorter, at the price of slower 5th and 6th calls,
  because the compiled code arrives later. On the six ladder benchmarks there is
  no tail gain. `loop_sum`'s p99 and max are *worse* in the background, and the compile cannot
  be why (it runs on the other thread, and that call is interpreted in both modes): the first
  call of a `loop_sum` process falls into one of a few speed groups, and in this measurement
  most background processes landed in the slow one. With ten processes per configuration the
  data cannot say whether `--jit-background` makes that more likely; this is unexplained (notes
  §5, Engine 5).

## One rung up close: stack VM to register VM

On `sieve`, `nbody` and `closures`, the register VM (row `05_register` over `04_nanbox`) is the
largest gain of any rung after leaving the tree-walker (inline caching gains more on `fib`, the
JIT on `loop_sum`), and it is the rung whose effect the VMs' own counters can show: the
tree-walker has no dispatch counter, and the JIT's machine code is invisible to the counters
(notes §5, Engine 4). The benchmark below is `sieve`, where the register VM gained the most.

**Instructions dispatched**, from the VM counters of a `debug` build (notes D5), for the script's
top level plus one call of `run()`. These are exact counts, not times, and they do not depend on
dispatch style or value representation, so the stack VM's column holds for rows 02 to 04. The
per-opcode counts are in [`docs/instruction_counts.txt`](docs/instruction_counts.txt), which the
`instruction-counts` ctest regenerates and compares; the rows below group them.

| `sieve`, one call | Stack VM | Register VM |
|---|---|---|
| Doing the work: `ADD MUL LE JUMP_IF_FALSE INDEX_GET INDEX_SET CALL CLOSURE GET_GLOBAL DEFINE_GLOBAL` | 8,051,972 | 8,051,972 |
| Moving values: `GET_LOCAL POP SET_LOCAL CONST FALSE TRUE NIL` | 19,949,723 | 0 |
| Loading a constant into a register: `LOADK LOADTRUE` | 0 | 5 |
| Jumping back or over: `LOOP JUMP` | 1,899,461 | 1,850,226 |
| Returning: `RETURN RETURN_NIL` | 2 | 2 |
| **Total** | **29,901,158** | **9,902,205** |

The work is identical, instruction for instruction; what disappears is moving values on and off
the stack. The inner marking loop (`flags[j] = false; j = j + i;` under `while (j <= n)`) shows
why. From `rung --dump-bytecode` and `rung --dump-bytecode --engine=register` on
`bench/sieve.rg`, one iteration is 16 stack instructions:

```
GET_LOCAL j; GET_LOCAL n; LE; JUMP_IF_FALSE; POP             // j <= n
GET_LOCAL flags; GET_LOCAL j; FALSE; INDEX_SET; POP          // flags[j] = false
GET_LOCAL j; GET_LOCAL i; ADD; SET_LOCAL j; POP              // j = j + i
LOOP
```

and 5 register instructions, because each one names its operands (`r0` is `n`, `r1` `flags`,
`r2` `i`, `r3` `j`; `k4` is the constant `false`):

```
LE r4 r3 r0; JUMP_IF_FALSE r4      // j <= n
INDEX_SET r1 r3 k4                 // flags[j] = false
ADD r3 r3 r2                       // j = j + i
JUMP
```

The 49,235 fewer jumps are the stack VM's `if` without `else`: after the `then` branch it jumps
over the `POP` that discards the condition on the other path, and the register VM has no such
`POP`.

**Time**, from `results/04_nanbox.json` and `results/05_register.json` (same `bench.py`
invocation, interleaved, neither noisy): the median call (`p50_ns`) went from 48.23 ms to
20.35 ms; the marginal table's 2.36× is the same comparison made on the median per-run totals.
The register VM dispatches 0.33 times as many instructions but takes more than 0.33 times as
long, so each register instruction costs more than a stack one (a 64-bit word to decode and a
constant-or-register flag to test per operand); how much more is not measured. No CPU-counter data (instructions retired, branch misses) exists
for this or any rung: Instruments' CPU Counters need a full Xcode install, which this machine
does not have (notes D5).

## Architecture

```
  source.rg -> lexer -> parser -> resolver -> [fold]      front end, the same for every engine
                                                 |
          +--------------------------------------+---------------------+
          |                       |                                    |
          v                       v                                    v
     tree-walker           stack compiler                      register compiler
    --engine=tree                 |                                    |
                                  v                           [superinstructions]
                              stack VM                                 |
                           --engine=stack                              v
                                                                 register VM
                                                     --engine=register, [inline cache]
                                                            |                ^
                                             hot function   |                |  bail-out: resume at
                                             (whitelisted)  v                |  the same bytecode
                                                       [baseline JIT] -------+  instruction
                                                   ARM64 code, --engine=jit
                                         (with --jit-background, compiled on a second thread)

  Every engine calls the shared runtime, src/runtime/: the Value type (tagged struct or
  [NaN-boxed]), arithmetic, comparison, printing and error messages, the heap and its
  mark-sweep garbage collector, interned strings.

  [brackets]: one ladder rung, switchable on its own. Computed-goto dispatch and NaN-boxed values
  are build options (CMake presets) shared by both VMs; the other rungs are command-line flags.
```

Every program goes through the same front end: the lexer makes tokens, the parser a syntax
tree, and the resolver works out where each variable lives (notes D11). `--fold` optionally
simplifies the tree. Then one engine runs it. The tree-walker runs the tree directly; the two
compilers turn it into bytecode for their VM (stack bytecode, or the register bytecode of notes
D14). The JIT is not a separate engine: it is the register VM, which hands hot functions that
fit its whitelist to an ARM64 code generator (notes D3, D16), either at once or, with
`--jit-background`, on a compiler thread while the VM keeps interpreting them (notes D8 has the
thread-safety and garbage-collection protocol). Machine code reads and writes the same register
slots the VM uses, so when a type guard fails it returns the index of the bytecode instruction
to resume at and the VM carries on from there, with nothing to translate. Every engine gets its
arithmetic, comparisons, printing, error messages and garbage collector from one shared runtime
(`src/runtime/`, notes D10), which is why they produce byte-identical output and why a rung can
change only how fast a program runs.

Source files: `src/lexer.cpp`, `parser.cpp`, `resolver.cpp`, `fold.cpp` (`--fold`),
`engine_tree.cpp`, `compiler_stack.cpp` and `vm_stack.cpp`, `compiler_reg.cpp`,
`superinstructions.cpp` (`--superinstructions`) and `vm_reg.cpp`, `src/jit/` (the ARM64
encoder, the code generator, executable memory and the compiler thread), and `src/runtime/`.

### The language

Deliberately tiny, because every feature has to be built once per engine: 32-bit integers,
64-bit floats, booleans, `nil`, immutable strings, fixed-size arrays, first-class functions with
closures, `let`, `if`, `while`, `for`, `return`, `print`, plus the native functions `array`,
`len` and `clock`.

```
fn fib(n) {
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2);
}
print fib(20);
```

The exact rules every engine must agree on (integer wraparound, division by zero, how floats
print, error messages and exit codes) are in [`docs/notes.md`](docs/notes.md), §2.

## What surprised me

<!-- DRAFT: written by the implementer from docs/notes.md section 5 and the results files.
     The owner rewrites this section in their own voice before issue #28 is closed. -->

> **DRAFT: the owner rewrites this in their own voice.** The paragraphs below are a neutral
> summary of what the data shows, taken from [`docs/notes.md`](docs/notes.md) §5.

NaN-boxing was expected to help most where the most memory is touched: it halves every value
from 16 bytes to 8, and `sieve` walks an array of 600,001 of them. The memory side did what was
predicted (the `heap` counters in `results/03_goto.json` and `results/04_nanbox.json`: `sieve`
allocates 192,002,178 bytes per process with tagged values and 96,002,018 NaN-boxed). The time
went the other way on all six benchmarks, and worst on `sieve`, the largest loss of any rung in
the ladder. The two rows were measured interleaved and no cell is noisy, so it is not noise;
why it happened was not measured, and notes §5 (rung 3b) lists three untested explanations:
costlier type checks, a differently compiled dispatch loop, and a suite that was never waiting
on memory. Two other rungs missed their prediction as well. Superinstructions cut `strcat`'s
dispatches by 36.5% and left its time unchanged, the clearest sign in the ladder that its time
is spent in the shared string runtime rather than in any interpreter. Inline caching went the
other way: a large gain on `fib` was called surprising beforehand, and it is the largest gain
any rung after the register VM gives `fib`.

The JIT compiles one function in the whole benchmark suite, `loop_sum`'s `run`. Every hot function in the
other five uses something the whitelist excludes: a global (which covers every call of a named
function, so all recursion, and the natives `array` and `len`), a float or string constant, a
closure or a captured variable. So the top of the JIT row's range is a single benchmark, and
even there the ratio mixes two things: without on-stack replacement the first of the 20 calls
in each process finishes in the interpreter, so `loop_sum`'s p99 is that interpreted call and
the gain for a compiled call alone is the change in p50 (42.55 ms in `results/08_fold.json`,
12.25 ms in `results/09_jit.json`). Compiling `run` took a median of 16.4 µs per process, far
too short to show up as a pause in a call that lasts tens of milliseconds. That is why the
background-compilation measurement needed its own warm-up benchmark: on the six ladder
benchmarks a second thread has nothing to remove, and only on `bench/warmup.rg`, where 64
compiles land in one short call, did the slowest calls get shorter. The tail measurement also
turned up something that is still unexplained: whenever `loop_sum`'s loop is interpreted with
the inline cache on (every call in rows `07_ic` and `08_fold`, the first call in `09_jit` and in
the background pair), its speed falls into one of a few distinct groups that depends on the
process, and nothing measured so far says why.

The JIT never crashed while it was being built: its unit tests and the conformance suite passed
under AddressSanitizer and UndefinedBehaviorSanitizer from their first run. The one crash near
it was not in generated code at all. On Linux arm64, in the sanitizer build only, calling
freshly written code crashed intermittently. The instruction cache was the first suspect and was
ruled out; the cause was UBSan's function-type check, which reads the 8 bytes in front of the
target of every call through a function pointer, and with the code at the very start of a fresh
memory mapping that read could fall on an unmapped page. Sixteen zero bytes in front of the
code fixed it. A single test run usually passed, so it was pinned down by running the test
hundreds of times in a loop in CI. Background compilation added no crash either, but it showed
a blind spot in ThreadSanitizer: on macOS it did not report a deliberately broken handoff
between the compiler thread and the engine while the code was copied with `memcpy`, and did once
the copy became plain 4-byte stores (notes D8).

## How to reproduce

### Building and running

Needs CMake 3.25+, Ninja, and Clang with C++20.

```sh
cmake --preset debug          # also: release, asan (Address + UB sanitizers), tsan, fuzz,
                                # release-goto and asan-goto (computed-goto dispatch),
                                # release-goto-nanbox and asan-goto-nanbox (+ NaN-boxed values),
                                # tsan-goto-nanbox (ThreadSanitizer with the JIT)
cmake --build --preset debug
ctest --preset debug
./build/debug/rung examples/hello.rg          # runs on the tree-walker (--engine=tree)
./build/debug/rung --engine=stack --stats examples/hello.rg   # stack VM; debug builds also count instructions
./build/debug/rung --engine=register --stats examples/hello.rg   # register VM, same counters
./build/debug/rung --engine=register --inline-cache --stats examples/hello.rg   # globals without hash lookups
./build/debug/rung --engine=register --superinstructions --stats=pairs examples/hello.rg   # fused pairs; which opcode follows which
# The JIT needs an arm64 CPU and NaN-boxed values, so a *-nanbox preset on an arm64 machine:
cmake --preset release-goto-nanbox && cmake --build --preset release-goto-nanbox
./build/release-goto-nanbox/rung --engine=jit --jit-log tests/conformance/jit/loop_sum.rg
#   --jit-log: each compile, rejection and bail-out to stderr; --jit-threshold=N (default 1000):
#   calls plus loop back-edges before a function is compiled
./build/release-goto-nanbox/rung --engine=jit --jit-background --jit-log bench/warmup.rg
#   --jit-background: compile on a second thread while the VM keeps running (notes D8)
./build/debug/rung --gc-stress --stats examples/hello.rg   # collect on every allocation; heap stats
./build/debug/rung --engine=register --fold --stats examples/hello.rg   # constant folding + dead-code removal
./build/debug/rung --dump-tokens examples/hello.rg
./build/debug/rung --dump-ast examples/hello.rg
./build/debug/rung --dump-bytecode examples/hello.rg                    # stack bytecode
./build/debug/rung --dump-bytecode --engine=register examples/hello.rg  # register bytecode
./build/release/rung --bench=20 --bench-out=out.json bench/fib.rg   # time 20 calls of run()
```

The six benchmark programs of the ladder live in `bench/`, with a seventh, `bench/warmup.rg`, a
plainly labelled warm-up benchmark (64 small functions that all become hot in the same call) for
comparing synchronous and background JIT compilation (notes D8); `--bench=N` runs one program's
top level and then times N calls of its `run()` function in C++, writing the per-call times to
the JSON file (notes D12). `bench/expected.json` holds each benchmark's checksum, which the
`release` preset's `bench-check-*` ctest tests verify on every engine (correctness only, never
timing).

### The timing tables and the summary

Benchmarks run only on the development machine (notes D5), never in CI. Plug the Mac in, turn
Low Power Mode off, close other apps, and leave it alone while it runs.

```sh
git status                                  # must be clean: results are tied to a commit
python3 scripts/bench.py                    # builds the presets, measures every configuration
python3 scripts/bench.py --configs jit_sync jit_background   # only the background-JIT pair (notes D8)
python3 scripts/ladder.py                   # rewrites the tables above and the summary at the top
python3 scripts/ladder.py --check           # what CI runs
```

`bench.py --configs 01_tree --benchmarks fib sieve --runs 5 --iterations 10` runs a subset. By
default each (configuration, benchmark) pair runs in 11 rounds of a fresh process that calls
`run()` 20 times. In every round all pairs run once, in an order shuffled by a recorded seed, so
background activity lands on every configuration alike. Round 1 is warm-up and discarded; the
other 10 give the median and interquartile range (IQR) of each run's total time, and the p50,
p99 and max over all per-iteration times pooled. A pair whose IQR exceeds 5% of its median is
flagged `noisy` in the results file and in the table; rerun it. Each results file also records
the CPU, macOS version, power source, compiler, git commit, date, run counts and seed, plus peak
memory (RSS), heap counters (objects and bytes allocated, collections) and, for JIT
configurations, the JIT's compile time per process. `bench.py` refuses to run on a dirty git
tree (`--allow-dirty` overrides this and records `dirty: true`), aborts if any benchmark returns
a result other than the one in `bench/expected.json`, and prints how a results file changed
before replacing it.

Figures quoted in prose (the before/after section and the draft above) name the results file
they come from: per-call `p50_ns`, the `heap` counters and `jit_compile_ns_median` are fields of
each benchmark in `results/<id>.json`.

### The counts

These count instead of timing, so they need no quiet machine, only a build with the VM counters
(the `debug` preset):

- `python3 scripts/instruction_counts.py --rung build/debug/rung` writes
  `docs/instruction_counts.txt`: the instructions each VM dispatches per benchmark, by opcode
  (the before/after table above groups its `sieve` section).
- `python3 scripts/pair_counts.py --rung build/debug/rung` writes `docs/pair_counts.txt`, the
  opcode pairs dispatched back to back that chose the superinstructions, and with
  `--superinstructions`, `docs/pair_counts_fused.txt`.
- `python3 tests/run_jit_coverage_check.py --rung build/release-goto-nanbox/rung` prints which
  functions the JIT compiles or rejects in each benchmark and checks the `‡` marks against it.

All three run as ctests (`instruction-counts`, `pair-counts` and `pair-counts-fused`,
`bench-jit-coverage`), which fail
if the committed files or marks no longer match what the code does.

## Testing

Five layers, each catching something the others cannot:

1. **Conformance tests** (`tests/conformance/<topic>/<name>.rg`). A Rung program with its
   expected output written in `// expect:` comments beside the code (format in
   [notes D13](docs/notes.md)). The runner executes every program on **every engine** and
   fails on any difference, so an engine that disagrees with the others, or with the
   [semantics contract](docs/notes.md), cannot pass. Run it with
   `python3 tests/run_conformance.py --rung build/debug/rung --engine tree [--gc-stress]
   [FILTER...]`; the format and how to add a test are in
   [`tests/conformance/README.md`](tests/conformance/README.md). `ctest` runs it once per
   engine, and once more per engine with `--gc-stress` (`conformance-tree`,
   `conformance-tree-gc-stress`, `conformance-stack`, `conformance-stack-gc-stress`,
   `conformance-register`, `conformance-register-gc-stress`, `conformance-jit`,
   `conformance-jit-gc-stress`), and once more per engine with `--fold`
   (`conformance-<engine>-fold`; the register VM also with `--gc-stress`), since folding must not
   change what any program does, and the register VM once more with `--inline-cache`
   (`conformance-register-inline-cache`, and with `--gc-stress`), and once more with
   `--superinstructions` (`conformance-register-superinstructions`, with `--gc-stress`, and with
   all the register-VM rungs on at once as `conformance-register-all-rungs`). The JIT runs the
   suite with `--jit-threshold=1`, so every function the JIT can compile is compiled on its first
   call, also with `--superinstructions` and with every rung on (`conformance-jit-fold`,
   `conformance-jit-superinstructions`, `conformance-jit-all-rungs`), and with `--jit-background`
   (`conformance-jit-background`, with `--gc-stress`, and with every rung); in a build without
   the JIT they are reported as skipped.
2. **Unit tests** (`tests/unit/`, [doctest](https://github.com/doctest/doctest)). Each C++
   module on its own: the lexer, parser, resolver, runtime and GC, the tree-walker, both
   compilers and both VMs, the ARM64 encoder (checked byte for byte against the LLVM
   assembler's encodings, committed as a table), and the JIT's whitelist and generated code (run
   directly on a register file), and the background compiler's handoff, GC rooting and shutdown.
   `ctest --preset debug` runs them.
3. **Sanitizers.** The `asan` preset builds everything with AddressSanitizer and
   UndefinedBehaviorSanitizer, and `tsan` with ThreadSanitizer. `tsan-goto-nanbox` is the
   ThreadSanitizer build with the JIT: it runs the unit tests and the conformance suite with the
   background compiler thread (notes D8). Warnings are errors. Run `asan` before every PR.
4. **Fuzzing.** A coverage-guided libFuzzer target feeds random bytes to the lexer, parser and
   resolver, and must never crash, hang, leak or trigger a sanitizer (details below). It stops
   before execution, because a valid Rung program may loop forever.
5. **Three-platform CI.** Every push builds and tests on macOS ARM64, Linux ARM64 and Linux
   x86-64 (inside the `Dockerfile`, with the JIT disabled), plus the fuzz job below and the
   `ladder.py --check` job. CI checks correctness only; it never measures speed.

### Fuzzing

`fuzz/fuzz_frontend.cpp` is the target; `fuzz/rung.dict` lists Rung's keywords and operators
for the mutator; `fuzz/run_fuzz.sh` runs it for a fixed time. The seed corpus is every
`tests/conformance/**/*.rg` and `examples/*.rg`. Inputs have no size cap: an expression more than
1000 links long (`1+1+...+1`, thousands of terms) is the compile error `expression chain too
long`, so it cannot overflow the native stack (the rule and how it was chosen: notes §2.6 and
[Q1](docs/notes.md)).

**libFuzzer needs a clang that ships its runtime, and Apple clang does not.**

- **Linux** (this is what CI uses): `sudo apt-get install clang cmake ninja-build`, then
  ```sh
  cmake --preset fuzz && cmake --build --preset fuzz
  fuzz/run_fuzz.sh build/fuzz/rung_fuzz_frontend 60
  ```
- **macOS**: install Homebrew LLVM (`brew install llvm`) and point CMake at it:
  ```sh
  cmake --preset fuzz -DCMAKE_CXX_COMPILER="$(brew --prefix llvm)/bin/clang++"
  cmake --build --preset fuzz
  fuzz/run_fuzz.sh build/fuzz/rung_fuzz_frontend 60
  ```
  Configuring `fuzz` with Apple clang stops with an error that says so.

`ctest --preset fuzz` replays the seed files once (no fuzzing) as a quick check. A failing run
writes the offending input to `fuzz-artifacts/`; CI uploads that directory as the `fuzz-crash`
artifact. Reproduce with `build/fuzz/rung_fuzz_frontend fuzz-artifacts/crash-<hash>`. Every bug
the fuzzer finds gets fixed and its input added as a unit or conformance test.

  follows `jlox` (environments as garbage-collected hash maps, variable uses resolved to a
  number of hops beforehand), and the stack VM and its compiler follow `clox` closely: local
  slots, scope tracking, upvalue resolution and jump patching in the compiler; the dispatch
  loop, calls and returns, and closures with Lua-style upvalues in the VM; the bytecode
  disassembler's layout. Anything that looks like `clox` probably is. The parser's precedence
  climbing is the same idea as `clox`'s Pratt parser, written as a table and a loop. The
  NaN-boxed `Value` follows the book's "Optimization" chapter too (quiet-NaN prefix, sign bit
  marking a pointer), with an int32 tag added.

  [*The Implementation of Lua 5.0*](https://www.lua.org/doc/jucs05.pdf) (2005). The basis for
  the register-based VM: locals in fixed registers with temporaries above them, compiling an
  expression into a chosen register, the calling convention (callee and arguments in
  consecutive registers, the result back in the callee's), one register file with each frame a
  window into it, and building long array literals in batches, as Lua's `SETLIST` does.
- The JIT's calling convention is the standard ARM64 procedure call standard (AAPCS64). Its
  instruction encoder is hand-written; its unit tests check every encoding against the LLVM
  assembler's output, which is used only to generate that test table and is not a dependency.
