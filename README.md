# Rung

**A small programming language, built five times over, to measure what each classic
interpreter speed-up is actually worth.**

C++20 · ARM64 machine code · garbage collection · multithreading · benchmarking ·
macOS and Linux

## What it is, simply

Rung is a tiny programming language I wrote in C++. You write a program like this:

```
fn fib(n) {
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2);
}
print fib(20);
```

and Rung runs it. What makes the project unusual is that I built **five different engines**
to run the same programs, from the simplest possible interpreter up to a JIT compiler that
turns hot functions into ARM64 machine code while the program is running. All five must print
exactly the same output for every program. The only thing allowed to change is speed.

Between the engines sits a "ladder" of optimizations. Each rung is the rung below it plus exactly
one change, so I can measure what that one change is worth on its own. That's where the name
comes from.

## Why I built it

Every explanation of how languages like Python, Lua or JavaScript get fast lists the same
techniques: compile to bytecode, use a register machine, pack values into 8 bytes, add a JIT.
They all say these help. I wanted to know *how much* each one helps, measured rather than
claimed, and I wanted to understand them well enough to build every one myself.

So I built the language once, then built the ladder one rung at a time and measured each step on
the same six programs on the same machine. Some steps paid off a lot. One made everything slower,
and it stays in the results table, because a result that didn't go my way is still a result.

- **Bytecode beats walking a tree.** The first bytecode VM is 1.30× to 4.99× faster than the
  tree-walking interpreter.
- **Registers beat a stack.** On `sieve`, the register VM does the same useful work as the
  stack VM in a third of the instructions ([details below](#one-rung-up-close-stack-vm-to-register-vm)).
- **The JIT is fast where it applies.** 22.64× faster than the tree-walker on `loop_sum`. But it
  only compiles functions in one of the six benchmarks, and I explain why below.
- **Not every optimization helps.** NaN-boxing halved the size of every value and made every
  benchmark slower.

## What's inside

- **Five engines, one shared runtime.** A tree-walking interpreter, a stack-based bytecode VM, a
  register-based VM, a baseline JIT, and a JIT that compiles on a background thread. All of them
  get their arithmetic, error messages and garbage collector from one shared module, which is
  why their output is byte-identical.
- **An ARM64 JIT with a hand-written instruction encoder.** No code-generation library: every
  instruction is encoded by hand and checked byte for byte against the LLVM assembler's
  output. Compiled code checks the types it assumed and, if one is wrong, hands control back to
  the VM in the middle of the function.
- **A background compiler thread.** Hot functions compile on a second thread while the program
  keeps running, with a release/acquire handoff that ThreadSanitizer checks.
- **A real runtime.** Mark-sweep garbage collection, interned strings, closures that capture
  variables, NaN-boxed values, computed-goto dispatch, superinstructions, inline caches, and
  constant folding.
- **Tested hard.** A conformance suite runs every test program on every engine and compares the
  output, also with garbage collection forced on every allocation and with every optimization
  switched on. On top of that: unit tests, AddressSanitizer, UBSan and ThreadSanitizer builds, a
  coverage-guided fuzzer, and CI on macOS ARM64, Linux ARM64 and Linux x86-64.
- **Honest benchmarking.** Benchmarks run in shuffled, interleaved rounds. Noisy measurements are
  flagged, and every result records the commit and machine it came from. The tables in this
  README are generated from those files, and CI fails if they don't match.

## Quick start

You need CMake 3.25+, Ninja and Clang with C++20.

```sh
cmake --preset debug && cmake --build --preset debug
ctest --preset debug                                    # unit + conformance tests

./build/debug/rung examples/fib.rg                      # tree-walking interpreter: 6765
./build/debug/rung --engine=stack examples/fib.rg       # stack VM, same output
./build/debug/rung --engine=register examples/counter.rg   # register VM, a closure: 2
./build/debug/rung --dump-bytecode examples/fib.rg      # see the bytecode
```

The JIT needs an ARM64 machine and the NaN-boxed build:

```sh
cmake --preset release-goto-nanbox && cmake --build --preset release-goto-nanbox
./build/release-goto-nanbox/rung --engine=jit --jit-log tests/conformance/jit/loop_sum.rg
```

`--jit-log` prints every function the JIT compiles or rejects, and every time compiled code hands
control back to the VM. More flags are in [Reproducing the numbers](#reproducing-the-numbers).

## The language

Deliberately tiny, because every feature has to be built once per engine: 32-bit integers that
wrap around, 64-bit floats, booleans, `nil`, immutable strings, fixed-size arrays, first-class
functions with closures, `let`, `if`, `while`, `for`, `return` and `print`, plus three built-in
functions, `array`, `len` and `clock`.

```
fn make_counter() {
  let count = 0;
  fn next() { count = count + 1; return count; }
  return next;
}
let counter = make_counter();
counter();
print counter();   // 2
```

The exact rules every engine has to agree on (integer wraparound, division by zero, how floats
print, every error message and exit code) are written down in [`docs/notes.md`](docs/notes.md)
§2.

## How it works

```
  source.rg -> lexer -> parser -> resolver -> [fold]      front end, the same for every engine
                                                 |
          +--------------------------------------+---------------------+
          |                       |                                    |
          v                       v                                    v
     tree-walker           stack compiler                      register compiler
    --engine=tree                 |                                    |
                                  v                           [superinstructions]
                              stack VM                                 |
                           --engine=stack                              v
                                                                 register VM
                                                     --engine=register, [inline cache]
                                                            |                ^
                                             hot function   |                |  bail-out: resume at
                                             (whitelisted)  v                |  the same bytecode
                                                       [baseline JIT] -------+  instruction
                                                   ARM64 code, --engine=jit
                                         (with --jit-background, compiled on a second thread)

  Every engine calls the shared runtime, src/runtime/: the Value type (tagged struct or
  [NaN-boxed]), arithmetic, comparison, printing and error messages, the heap and its
  mark-sweep garbage collector, interned strings.

  [brackets]: one ladder rung, switchable on its own. Computed-goto dispatch and NaN-boxed values
  are build options (CMake presets) shared by both VMs; the other rungs are command-line flags.
```

1. **The front end** is shared by every engine. The lexer turns text into tokens, the parser
   builds a syntax tree, and the resolver works out where every variable lives (a local slot, a
   captured variable, or a global) and reports errors like using a variable before it's
   declared. `--fold` can simplify the tree first.
2. **The engines.** The tree-walker runs the syntax tree directly. The two compilers turn it into
   bytecode: one for the stack VM, one for the register VM.
3. **The JIT** isn't a separate engine. It's the register VM plus a code generator. When a
   function gets hot and only uses operations the JIT supports, it's compiled to ARM64. The
   machine code reads and writes the same register slots the VM uses, so if one of its type
   checks fails (say, a float turns up where it assumed an integer), it simply returns the
   bytecode position to resume at and the VM carries on from there.
4. **The shared runtime** in `src/runtime/` gives every engine the same values, arithmetic,
   printing, error messages and garbage collector. That's what makes the comparison fair: a rung
   can only change how fast a program runs, never what it does.

### The ladder

| Rung | What it changes | The idea |
|---|---|---|
| `01_tree` | Tree-walking interpreter | Run the syntax tree directly. The baseline. |
| `02_stack` | Stack-based bytecode VM | Compile to compact bytecode and run it in a tight loop. |
| `03_goto` | Computed-goto dispatch | Jump straight from one instruction's handler to the next, instead of going back through one `switch`. |
| `04_nanbox` | NaN-boxed values | Pack every value into 8 bytes by hiding integers and pointers inside unused floating-point "not a number" patterns. |
| `05_register` | Register-based VM | Instructions name their operands directly, so far fewer instructions only move values around. |
| `06_super` | Superinstructions | Fuse the most common instruction pairs into one. |
| `07_ic` | Inline caching for globals | Remember where each global variable lives instead of looking it up by name every time. |
| `08_fold` | Constant folding | Compute things like `2 * 3` once, before the program runs. |
| `09_jit` | Baseline JIT | Compile hot functions to ARM64 machine code. |

Each rung keeps everything below it, so row 09 is the register VM with every optimization on
plus the JIT. A tenth configuration, the background compiler thread, is measured separately.

## One rung up close: stack VM to register VM

The register VM (`05_register` over `04_nanbox`) is the biggest single gain after leaving the
tree-walker on `sieve`, `nbody` and `closures`. It's also the rung the VMs' own instruction
counters can explain, so here it is on `sieve`.

**Instructions dispatched** for the script's top level plus one call of `run()`, counted by
the VMs themselves in a `debug` build. These are exact counts, not times. The per-opcode counts
are in [`docs/instruction_counts.txt`](docs/instruction_counts.txt), which a test regenerates and
compares.

| `sieve`, one call | Stack VM | Register VM |
|---|---|---|
| Doing the work: `ADD MUL LE JUMP_IF_FALSE INDEX_GET INDEX_SET CALL CLOSURE GET_GLOBAL DEFINE_GLOBAL` | 8,051,972 | 8,051,972 |
| Moving values: `GET_LOCAL POP SET_LOCAL CONST FALSE TRUE NIL` | 19,949,723 | 0 |
| Loading a constant into a register: `LOADK LOADTRUE` | 0 | 5 |
| Jumping back or over: `LOOP JUMP` | 1,899,461 | 1,850,226 |
| Returning: `RETURN RETURN_NIL` | 2 | 2 |
| **Total** | **29,901,158** | **9,902,205** |

The useful work is identical, instruction for instruction. What disappears is moving values on
and off the stack. The inner loop (`flags[j] = false; j = j + i;` under `while (j <= n)`) shows
why. In stack bytecode one iteration is 16 instructions:

```
GET_LOCAL j; GET_LOCAL n; LE; JUMP_IF_FALSE; POP             // j <= n
GET_LOCAL flags; GET_LOCAL j; FALSE; INDEX_SET; POP          // flags[j] = false
GET_LOCAL j; GET_LOCAL i; ADD; SET_LOCAL j; POP              // j = j + i
LOOP
```

In register bytecode it's 5, because each instruction names its operands (`r0` is `n`, `r1` is
`flags`, `r2` is `i`, `r3` is `j`, and `k4` is the constant `false`):

```
LE r4 r3 r0; JUMP_IF_FALSE r4      // j <= n
INDEX_SET r1 r3 k4                 // flags[j] = false
ADD r3 r3 r2                       // j = j + i
JUMP
```

**Time.** In `results/04_nanbox.json` and `results/05_register.json` (measured in the same
session, interleaved, neither noisy) the median call went from 48.23 ms to 20.35 ms. A third of
the instructions took more than a third of the time, so each register instruction costs a bit
more than a stack one: it's a wider word to decode, and each operand can be a register or a
constant. I haven't measured exactly how much more, and I have no CPU-counter data (instructions
retired, branch misses) for any rung, because that needs a full Xcode install.

## What surprised me

I expected NaN-boxing to help, especially on `sieve`, where smaller values should make the large array cheaper to work with. It did cut values from 16 bytes to 8, and total heap allocation per process (20 calls) fell from about 192 MB to 96 MB (`results/03_goto.json` and `results/04_nanbox.json`). But every benchmark got slower. `sieve` had the biggest loss, at 0.63× the speed of the previous row. I don't know why yet: more expensive type checks, changes to the compiled dispatch loop, and a workload that wasn't limited by memory are all possible explanations, but none has been tested. Superinstructions gave me another result I hadn't expected: `strcat` dispatched 36.5% fewer instructions with almost no change in time. That suggests the string runtime is where most of its time goes, although I haven't confirmed that with a profile. Inline caching went the other way: `fib` gained 1.46×, more than I expected (`results/06_super.json` and `results/07_ic.json`; these two rows were measured in separate `bench.py` runs, so the ratio is not an interleaved comparison).

The JIT result needs some context. The 22.64× speedup over the tree-walker is for `loop_sum`, the only one of the six benchmarks where a function actually compiles. The others hit unsupported operations and keep running in the register VM. Even on `loop_sum`, the first call finishes in the interpreter because there is no on-stack replacement. Comparing the median call times gives a clearer view of the compiled calls: 42.55 ms before the JIT and 12.25 ms after (`results/08_fold.json` and `results/09_jit.json`, from separate runs). Compilation itself took about 16 µs, so moving it to another thread didn't produce a measurable tail-latency gain on the main suite. On `warmup`, a separate benchmark built to make 64 functions become hot together, background compilation reduced p99 from 0.82 ms to 0.32 ms (`results/jit_sync.json` and `results/jit_background.json`). Some later calls were slower because the code wasn't ready yet. I can point to a benefit on that test, but I can't generalize it to the whole suite. `loop_sum` also has an unresolved oddity: interpreted calls fall into distinct speed groups across processes, and its background tail was worse in this measurement. I don't have an explanation for that yet.

I thought generated machine code would be the most likely place for a crash. The baseline JIT tests passed from their first run; the intermittent crash around executable memory came from a sanitizer check on Linux ARM64. Before an indirect call, UBSan reads the eight bytes before the function's address. When the code started at the beginning of a mapped page, that read could reach unmapped memory. Leaving 16 zero bytes before the code fixed it. About 5% of runs crashed, so a single run usually passed; the cause was found by looping the test 300 to 600 times in CI (notes §5). The background compiler exposed a different problem with testing: on macOS, ThreadSanitizer missed a deliberately broken handoff while code was copied with `memcpy`. Plain four-byte stores, together with a C++ read of the code before execution, made the broken handoff detectable. That made me more careful about treating a clean sanitizer run as evidence: it matters whether the sanitizer can see the accesses being checked.

## Limitations and what I'd do next

- **The JIT covers a narrow slice of the language.** It compiles integer arithmetic,
  comparisons, jumps and array reads and writes. Calls, globals, floats, strings and closures
  stay in the VM, which is why it compiles one benchmark out of six. Compiling `fib` would need
  direct self-recursion. `sieve`'s loops already compile when they're handed the array, but its
  function also calls the built-in `array`, and calls are outside what the JIT supports.
- **No on-stack replacement.** A function that gets hot in the middle of a long call finishes
  that call in the interpreter, and only later calls run as machine code.
- **NaN-boxing's slowdown is unexplained.** My candidate explanations (costlier type checks, a
  differently compiled dispatch loop, a suite that was never waiting on memory) are all untested.
- **One machine, one suite.** Every number comes from one M1 Pro, and the superinstructions
  were chosen from this suite's own instruction-pair counts, so they are tuned to it.
- **The JIT is ARM64-only.** On x86-64, Rung runs on the four other engines.

## Testing

Five layers, each catching something the others can't:

1. **Conformance tests** (`tests/conformance/`). Rung programs with their expected output written
   in `// expect:` comments. The runner executes every program on every engine and fails on any
   difference. `ctest` runs the suite on every engine, again with garbage collection forced on
   every allocation, and again with each optimization flag and all of them at once. The JIT runs
   it with a threshold of 1, so every function it can compile is compiled on its first call. How
   to add a test is in [`tests/conformance/README.md`](tests/conformance/README.md).
2. **Unit tests** (`tests/unit/`, [doctest](https://github.com/doctest/doctest)). Every module on
   its own, including the ARM64 encoder against the LLVM assembler's encodings and the
   background compiler's handoff, garbage-collection rooting and shutdown.
3. **Sanitizers.** `asan` builds everything with AddressSanitizer and UndefinedBehaviorSanitizer,
   `tsan` with ThreadSanitizer, and `tsan-goto-nanbox` is ThreadSanitizer with the JIT and its
   compiler thread. Warnings are errors.
4. **Fuzzing.** A libFuzzer target feeds random bytes to the lexer, parser and resolver. It found
   that a long flat chain like `1 + 1 + ... + 1` could overflow the native stack. Such chains are
   now a compile error past 1000 links.
5. **CI on three platforms.** Every push builds and tests on macOS ARM64, Linux ARM64 and Linux
   x86-64 (in Docker, without the JIT), runs the fuzzer, and checks that the README tables match
   the committed results. CI checks correctness only; it never measures speed.

<details>
<summary>Running the fuzzer</summary>

`fuzz/fuzz_frontend.cpp` is the target, `fuzz/rung.dict` lists the language's keywords and
operators for the mutator, and the seed corpus is every conformance test and example. libFuzzer
needs a Clang that ships its runtime, which Apple Clang doesn't.

- **Linux** (what CI uses): `cmake --preset fuzz && cmake --build --preset fuzz`, then
  `fuzz/run_fuzz.sh build/fuzz/rung_fuzz_frontend 60`.
- **macOS**: install Homebrew LLVM, then
  `cmake --preset fuzz -DCMAKE_CXX_COMPILER="$(brew --prefix llvm)/bin/clang++"`, build, and run
  the same script.

A failing run writes the input to `fuzz-artifacts/`, and CI uploads it. Every bug the fuzzer
finds gets fixed and its input becomes a test.
</details>

## Reproducing the numbers

Every speed figure in this repository comes from one pipeline. `scripts/bench.py` measures the
configurations in `scripts/ladder_configs.json` and writes `results/<id>.json`, and
`scripts/ladder.py` turns those files into the tables above.

```sh
git status                      # must be clean: results are tied to a commit
python3 scripts/bench.py        # builds the presets and measures every configuration
python3 scripts/ladder.py       # regenerates the tables and the summary in this README
python3 scripts/ladder.py --check   # what CI runs
```

Run benchmarks with the machine plugged in, Low Power Mode off and nothing else running. Each
configuration and benchmark runs in 11 rounds of a fresh process that calls `run()` 20 times. In
every round the order is shuffled with a recorded seed, so background noise lands on all of them
alike. The first round is a warm-up and is discarded. A measurement whose spread (interquartile
range) is over 5% of its median is flagged as noisy. Every results file records the CPU, OS,
power source, compiler, git commit and date, plus peak memory, garbage-collector counters and
the JIT's compile time.

<details>
<summary>Every command-line flag</summary>

```sh
rung [--engine=tree|stack|register|jit] program.rg
  --stats                 heap statistics; instruction counts in debug builds
  --stats=pairs           which instruction follows which (register and stack VMs)
  --gc-stress             collect garbage on every allocation
  --fold                  constant folding and dead-code elimination
  --superinstructions     fused instruction pairs (register VM, JIT)
  --inline-cache          cached global lookups (register VM, JIT)
  --jit-threshold=N       calls plus loop iterations before a function is compiled (default 1000)
  --jit-log               log every compile, rejection and bail-out
  --jit-background        compile on a second thread
  --dump-tokens | --dump-ast | --dump-bytecode
  --bench=N --bench-out=FILE   time N calls of the program's run() function
```

The counting tools need no quiet machine, only a `debug` build:
`scripts/instruction_counts.py` writes `docs/instruction_counts.txt`, `scripts/pair_counts.py`
writes the instruction-pair counts that chose the superinstructions, and
`tests/run_jit_coverage_check.py` reports which functions the JIT compiles in each benchmark.
Each runs as a test that fails if the committed files no longer match the code.
</details>

## Project layout

```
src/                  the language: front end, engines, compilers
  runtime/            values, garbage collector, arithmetic and errors shared by every engine
  bytecode/           stack and register instruction formats
  vm/                 dispatch macros and instruction counters shared by both VMs
  jit/                ARM64 encoder, code generator, executable memory, compiler thread
tests/conformance/    Rung programs with expected output, run on every engine
tests/unit/           C++ unit tests
bench/                the benchmark programs and their expected checksums

fuzz/                 the libFuzzer target
```
